# 跟随上游，不自动覆盖现网

## 三条不同的更新路径

| 内容 | 来源 | 当前方式 |
| --- | --- | --- |
| 基础域名/IP规则数据 | `ryuu-restart/agent-route/release` | 候选provider直接指向上游；客户端按86400秒刷新 |
| 规则构建器、模板和文档 | `ryuu-restart/agent-route/master` | 手动fetch、审阅、merge、测试，保留上游来源 |
| 本机适配层 | 本Fork的`custom/network-environment` | 只改`custom/network/`及最小入口，核验后正常提交；生产部署另行授权 |

**Fork不会自动同步源码，也不会自动维护本机AI域名和应用路径。** 本分支没有创建自动同步任务、启用Fork计划发布或改客户端provider地址。GitHub的Fork继承工作流通常需要显式启用；即使执行成功，源码同步、规则发布与用户设备重载仍是三件事。

## 首次获取

```bash
git clone --branch custom/network-environment https://github.com/caaaptaintop/agent-route.git
git -C agent-route remote add upstream https://github.com/ryuu-restart/agent-route.git
```

本机已有remote时先查看，不重复添加、不覆盖不同连接。不要把token写进remote URL。

## 审阅并合并源码

先确认工作树干净；存在未提交工作时不要覆盖、clean或reset。

```bash
git status --short
git fetch upstream
git switch custom/network-environment
git log --oneline HEAD..upstream/master
git diff HEAD...upstream/master -- .github scripts docs examples AGENTS.md README.md
git merge upstream/master
node custom/network/test_prepare.js
node custom/network/test.js
node custom/network/test_scope.js
node custom/network/test_groups.js
node custom/network/test_dns_exception.js
```

冲突时按本地适配目标与新上游规则语义合并，不能直接用一方全覆盖。审阅上游维护说明及依赖后再运行其完整测试、契约检查和原生验证；本分支自有测试不是上游全套测试的替代。通过后才正常push定制分支，不force-push：

```bash
git push origin custom/network-environment
```

`master`保持上游用途；如果以后要更新Fork的master，应先确认它没有独立改动，再做快进同步。本次不将master改成定制默认分支。打开仓库时选择定制分支才能看到本层入口。

## release分支不能当源码合并

上游`release`是滚动数据快照，可能以无历史提交强推，不要merge/rebase进定制源码分支，也不能依赖分支历史找回旧规则代。若未来要自己发布规则：

1. 先独立审阅并启用构建/验证/最小权限发布流程，核对实际发布字节和manifest；不能只同步master就声称有规则数据。
2. 确认自己Fork的`release`确有可下载且通过校验的五类规则及清单。
3. 在隔离候选中改provider URL、测试并准备回退，再经授权替换生产。不要仅把owner字符串换掉就上线。
4. 源数据构建的CI验证不是本机DNS/WebRTC、IPv6或真实故障演练。

## 版本与回退

- 源码采用正常提交记录；可通过`git show`比较已知版本，回退代码使用正常revert，不改写远程历史。
- 源码回退不代表客户端配置已回退；部署需单独核验真实规则、provider、组选择与联网。
- 生成的本地pins及候选不推送，本机先保留当前可回切状态；不额外制作敏感备份。
- 若自动生成器报告节点身份变化，应停止发布并核实，不从上游同步或重新生成摘要来掩盖它。
- 后续若要无人值守跟进，先明确只读审阅/提PR/发布/部署的授权范围；本次未启用任何一种。
